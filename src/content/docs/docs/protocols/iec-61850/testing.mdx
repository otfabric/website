OT Fabric tests its IEC 61850 stack against four independent implementations, in both directions: OT Fabric as client, subscriber or publisher against a reference stack, and the reference stack against the OT Fabric server, subscriber or publisher. This page lists the tools, how to run them, and exactly what the evidence covers. It describes iec61850-interop v1.0.1, go-mms v1.2.1, go-iec61850 v1.2.1 and iec61850ctl v0.4.0.

<Aside type="caution">
Interoperability has been shown against four software stacks: libiec61850, IEC61850bean, dscsystems/go-iec61850 and iec61850-rust. It is not conformance testing, the libraries have no UCA certification, and interoperability with physical IEDs (protection relays, meters, bay controllers, merging units) has not yet been formally established. Validate against your own devices, read-only first.
</Aside>

## Simulators you can run locally

| Simulator | What it is | Good for |
|---|---|---|
| `iec61850ctl server start --scl file.icd` | The go-iec61850 server driven by any ICD, CID or SCD, with optional value seeding from a live device | Trying reads, reports and controls against your own model |
| go-iec61850 `NewServer` | The same server embedded in your Go program, with `RegisterControl`, `SetValue`, the report engine, and GOOSE and SV publishing | Test fixtures in Go code |
| go-iec61850 `goose.NewHub`, `sv.NewHub` | In-memory Ethernet with fault injection (loss, duplication, reordering, corruption) | GOOSE and SV tests without privileges or a network |
| `<stack>-ied-server` (iec61850-interop) | The IED server of libiec61850, IEC61850bean, dscsystems or iec61850-rust, loaded with the interop fixture | Independent C, Java, Go and Rust references |
| `<stack>-goose-publisher`, `<stack>-sv-publisher` (iec61850-interop) | GOOSE and SV publishers of libiec61850, dscsystems and iec61850-rust | Independent traffic for a subscriber under test |
| `libiec61850-mms-server` (iec61850-interop) | Generic MMS server (no IEC 61850 model) | Raw MMS with go-mms |

Self-tests where an OT Fabric client talks to an OT Fabric server are useful for smoke testing but are not interoperability evidence.

## iec61850-interop

[iec61850-interop](https://github.com/otfabric/iec61850-interop) publishes one container image per independent IEC 61850 stack, the fixtures every stack loads, and the JSON Lines contract every adapter command speaks. It owns the images and fixtures, not the assertions: those live in go-mms, go-iec61850 and iec61850ctl. Until v0.4.1 it was called mms-interop; it was renamed at v1.0.0 because it now covers MMS, IED services, GOOSE and Sampled Values. From v1.0.0 the image names, commands, flags, event shapes, exit codes and fixture revisions follow semantic versioning.

| Stack | Upstream | Language | Licence | Pinned at |
|---|---|---|---|---|
| libiec61850 | [mz-automation/libiec61850](https://github.com/mz-automation/libiec61850) | C | GPL-3.0 | `1.6.2.1-89-g6e265c54` |
| IEC61850bean | [beanit/iec61850bean](https://github.com/beanit/iec61850bean) | Java | Apache-2.0 | 1.9.0 |
| dscsystems | [dscsystems/go-iec61850](https://github.com/dscsystems/go-iec61850) | Go | GPL-3.0 | `v0.6.5-1-g6bf3f37` |
| iec61850-rust | [csp0924/iec61850-rust](https://github.com/csp0924/iec61850-rust) | Rust | MIT OR Apache-2.0 | `v0.2.0` |

The four share no protocol code with each other or with the OT Fabric libraries. The GPL stacks run in their own containers and are never linked into OT Fabric code.

| Image | MMS server, client | IED server, client, controller, reporter | GOOSE publisher, subscriber | SV publisher, subscriber | SVCB over MMS |
|---|:-:|:-:|:-:|:-:|:-:|
| `ghcr.io/otfabric/iec61850-interop-libiec61850` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `ghcr.io/otfabric/iec61850-interop-iec61850bean` | | ✓ | | | |
| `ghcr.io/otfabric/iec61850-interop-dscsystems` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `ghcr.io/otfabric/iec61850-interop-iec61850-rust` | ✓ | ✓ | ✓ | ✓ | |

Every image is multi-arch (`linux/amd64`, `linux/arm64`), and every GitHub release lists the image digests and ships a `manifest.json` with them and the upstream pins. The authoritative capability claim, with each stack's known limitations, is `fixtures/capabilities.json` in the repository.

### Fixtures

| Revision | Content |
|---|---|
| `mms-v2` | Generic MMS: variables of every type, named variable lists, Status, information reports, journals and a file store |
| `iec61850-v3` | The IED `InteropIED` with logical device `InteropLD`: `GGIO1` (SPS, DPS, controls `SPCSO1/2/3` for direct, SBO and SBOw, writable `SetInt1.setVal[SP]`), `MMXU1.TotW`, `MMTR1.TotVAh`, dataset `dsInterop`, `urcb01` and `brcb01`, and the SV control block `MSVCB02` |
| `goose-v1` | GoCBs `gcbAll` (eight members: boolean, integer, unsigned, float32, quality, UTC time, Dbpos and a nested MV structure) and `gcbBool`, with GSE addresses and initial and update values |
| `sv-v1` | A 9-2LE merging unit (`MSVCB01`, 80 samples per period at 50 Hz, one ASDU) and a generic stream (`MSVCB02`, 1000 samples/s, four ASDUs per frame, every optional field) |

### Adapter contract

A server or publisher prints one readiness line on stdout before it accepts connections or sends; client and subscriber adapters print one JSON line per operation or frame. Diagnostics go to stderr. A step a stack does not implement answers `{"event":"error","code":"unsupported",...}` and exits `4`, so the test skips it with that reason. The full contract is in `docs/contract.md`.

```text
{"event":"ready","address":"0.0.0.0:1102","fixture":"mms-v2",...}
{"operation":"read","target":"InteropIEDInteropLD/GGIO1.DPS1.stVal[ST]","ok":true,"value":2}
```

### Starting an adapter by hand

<Tabs>
  <TabItem label="MMS and IED services">
    ```sh
    V=v1.0.1
    R=ghcr.io/otfabric/iec61850-interop
    docker run --rm -p 1102:1102 --entrypoint libiec61850-ied-server \
      $R-libiec61850:$V --port 1102
    ```

    Then point iec61850ctl at it:

    ```sh
    export IEC61850_HOST=127.0.0.1 IEC61850_PORT=1102 IEC61850_IED_NAME=InteropIED
    iec61850ctl list lds --format json
    iec61850ctl get object --object InteropLD/MMXU1.TotW.mag.f --fc MX --format json
    ```
  </TabItem>
  <TabItem label="GOOSE">
    GOOSE is layer 2, so both ends need `NET_RAW` on one named bridge:

    ```sh
    docker network create -o com.docker.network.bridge.name=goose0 iec61850-interop-goose
    docker run -i --rm --network iec61850-interop-goose --cap-add NET_RAW \
      --entrypoint libiec61850-goose-publisher $R-libiec61850:$V \
      --iface eth0 --gocb-ref 'InteropIEDInteropLD/LLN0$GO$gcbBool' --go-id InteropGooseBool \
      --dataset 'InteropIEDInteropLD/LLN0$dsGooseBool' --app-id 0x1002 --dst 01:0c:cd:01:00:02 \
      --values '[{"type":"boolean","value":false},{"type":"bit-string","value":"0000000000000"}]'
    ```

    On a Linux host, `goose0` is a port of the same segment: `sudo iec61850ctl goose sniff --iface goose0`. On macOS and Windows the bridge lives in Docker Desktop's VM, so run the other side in a container on the same network.
  </TabItem>
  <TabItem label="Sampled Values">
    `scripts/sv-crosscheck.sh` in the repository runs a publisher and a subscriber on a bridge and checks values, header fields and loss (at most 1%) against `fixtures/sv/sv.json`:

    ```sh
    scripts/sv-crosscheck.sh $R-dscsystems:$V dscsystems-sv-publisher \
                             $R-libiec61850:$V libiec61850-sv-subscriber
    ```
  </TabItem>
</Tabs>

To drive the OT Fabric server with a reference client, start `iec61850ctl server start --host 0.0.0.0 --port 1102 ...` on the host and run the adapter with `--add-host=host.docker.internal:host-gateway --host host.docker.internal`.

## Running the suites

The suites need Docker. Tests start each adapter with `docker run`, wait for the readiness line, run, and tear down. Nothing has to be running beforehand. The CI of each repository pins the images by digest.

<Tabs>
  <TabItem label="go-mms">
    ```sh
    make interop                                   # libiec61850
    MMS_INTEROP_STACK=dscsystems make interop
    make interop-all                               # every peer stack
    ```
    Tests are behind `-tags=interop`. Each scenario has one test body that runs against the stack selected by `MMS_INTEROP_STACK`; peer limitations are explicit per-stack quirks or skips with reasons.
  </TabItem>
  <TabItem label="go-iec61850">
    ```sh
    make interop                                   # MMS, against libiec61850 and IEC61850bean
    IEC61850_PEER_STACK=iec61850-rust make interop
    GOOSE_IFACE=goose0 make interop-goose          # GOOSE and SV, Linux, needs CAP_NET_RAW
    ```
    The `TestLibIEC*` suites are parametrized by `IEC61850_PEER_STACK` (`libiec61850`, `dscsystems` or `iec61850-rust`); IEC61850bean has its own `TestBean*` suites. The GOOSE and SV tests run against every stack that has the commands.
  </TabItem>
  <TabItem label="iec61850ctl">
    ```sh
    make build-nocheck
    make e2e                                       # the four client stacks and self
    IEC61850CTL_E2E_STACKS=goose-libiec61850 make e2e
    IEC61850CTL_E2E_STACKS=sv-dscsystems make e2e
    IEC61850CTL_E2E_STACKS=all make e2e            # every CI direction
    ```
    The e2e package runs the built binary as a black box. `e2e/testdata/interop.lock.json` pins the images by commit and digest.
  </TabItem>
</Tabs>

A test skipped without a registered limitation fails CI.

<Aside type="note">
At the time of writing, go-mms, go-iec61850 and iec61850ctl pin the last images published under the old name (mms-interop v0.4.0 and v0.4.1). iec61850-interop v1.0.0 has the same adapters, commands and fixtures under the new image names, so moving the pins changes no test.
</Aside>

## What has been validated

### go-mms

Every scenario runs in both directions, go-mms client against the stack's MMS server and the stack's MMS client against the go-mms server: association, Identify, Status, GetNameList, type descriptions, reads and writes of every fixture type with alternate access, named variable lists in domain, VMD and association scope, information reports, file services (directory, open, read with initial position, delete, rename, ObtainFile), journals, and abort in both directions.

| Stack | Result | Notes |
|---|---|---|
| libiec61850 | 120 pass | Its server sends only the named-list form of information reports and ignores the FileOpen initial position; both are asserted, not skipped |
| dscsystems | 112 pass, 8 skip | Its client reads and writes whole variables only, and has no association-specific or writable named variable lists |
| iec61850-rust | 120 pass | Its documented limits (ObtainFile, named variable list deletion, in-memory file store) are asserted |
| IEC61850bean | 14 pass | IED server tests only; the image has no generic MMS server or client |

Extending this suite to every public method found the FileDirectory bug (go-mms issue #2) and fifteen further wire and behaviour bugs, all fixed in go-mms v1.1.0.

### go-iec61850

| Area | libiec61850 | IEC61850bean | dscsystems | iec61850-rust |
|---|:-:|:-:|:-:|:-:|
| Go client → stack server: browse, read and write, datasets | ✓ | ✓ | ✓ | ✓ |
| Stack client → Go server: browse, read and write, datasets | ✓ | ✓ | ✓ | ✓ |
| URCB reporting, both directions | ✓ | ✓ ¹ | ✓ | ✓ |
| Direct and SBO control, both directions | ✓ | ✓ | ✓ | ✓ |
| SBOw (enhanced security) | ✓ | skip ² | ✓ ³ | ✓ |
| CDC reads of DPS and BCR, both directions | ✓ | ✓ | ✓ | ✓ |
| MMS file services | ✓ | ✓ | ✓ | not in stack |
| GOOSE: Go publisher → stack subscriber | ✓ | n/a | ✓ | ✓ |
| GOOSE: stack publisher → Go subscriber, validated from SCL | ✓ | n/a | ✓ | ✓ |
| GOOSE: Go IED server GoCB → stack subscriber | ✓ | n/a | ✓ | ✓ |
| SV: Go publisher → stack subscriber, 9-2LE and generic | ✓ ⁴ | n/a | ✓ | ✓ |
| SV: stack publisher → Go subscriber, validated from SCL | ✓ | n/a | ✓ | ✓ |
| SV: Go IED server MSVCB → stack subscriber | ✓ | n/a | ✓ | ✓ |
| MSVCB over MMS, Go client → stack server | ✓ | n/a | ✓ | not in stack |

¹ The IEC61850bean server does not support URCB reservation; that negative test is skipped.
² The IEC61850bean server does not expose `SBOw[CO]` as writable.
³ The dscsystems controller waits for CommandTermination, which the go-iec61850 server sends since v1.1.0. That test found the gap.
⁴ libiec61850's SV subscriber accepts `smpMod` only as one octet and drops ASDUs with the two-octet form that go-iec61850 and libiec61850's own publisher send, so the generic stream is skipped for that subscriber and the 9-2LE stream is checked. The go-iec61850 subscriber accepts both widths, which iec61850-rust needs.

The suites also cover BRCB EntryID resume and overflow, the integrity period (skipped against iec61850-rust, which enforces the fixture's fixed `TrgOps` and `IntgPd`), quality and timestamps, multi-client scenarios, negative cases, GOOSE retransmission and supervision timeouts, and SV header fields, optional fields and loss accounting. The per-stack matrix and every deviation are in go-iec61850's [COMPATIBILITY.md](https://github.com/otfabric/go-iec61850/blob/main/COMPATIBILITY.md) and [INTEROP.md](https://github.com/otfabric/go-iec61850/blob/main/INTEROP.md).

### iec61850ctl end to end

The CLI suite runs the built binary against all four stacks, in 19 CI jobs:

- **Client journeys** against every IED server: browse and reads against expected values, datasets, RCB discovery, URCB GI subscription in JSON Lines, `control operate` on SPCSO1/2/3 with `--confirm-ref`, `set object` with `--verify`, BRCB purge and resume by EntryID, and negative cases. SBOw against IEC61850bean and BRCB reads against iec61850-rust are asserted as expected failures.
- **Reverse journeys**: every stack's controller, reporter and reader against `iec61850ctl server start`.
- **GOOSE**, against libiec61850, dscsystems and iec61850-rust: each stack's publisher into `goose subscribe` and `goose sniff`, and `goose publish` into each stack's subscriber, with both states, every value, the control block fields and the supervision timeout checked.
- **Sampled Values**, against the same three stacks and for both streams: `sv subscribe` and `sv sniff` against each publisher and `sv publish` into each subscriber, with value, header and loss assertions, plus `sv svcb get` of `MSVCB02` over MMS.

## Not yet validated

- Physical IEDs and merging units from any vendor, and commercial IEC 61850 stacks.
- Conformance testing to the UCA test procedures.
- SV timing under real load: the publisher is software-timed and has no PTP or 1PPS synchronization.
- Edition 2.1 (2007B4) features beyond those listed.
- Dynamic dataset creation on the server, the client's wait for CommandTermination, and TimeActivatedOperate (not implemented).
- R-GOOSE, R-SV and IEC 62351-6 (not implemented). dscsystems implements them, so they could be tested once go-iec61850 does.
