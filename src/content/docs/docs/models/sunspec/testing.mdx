SunSpec has its own interoperability suite, [sunspec-interop](/projects/sunspec-interop/): independent SunSpec implementations in containers, behind one command-line contract, with deterministic fixtures. The Modbus transport under go-sunspec is tested separately, against five Modbus stacks (see the [Modbus testing page](/docs/protocols/modbus/testing/)). This page covers both, how go-sunspec and sunspecctl are tested without hardware, and how to test your own SunSpec code without an inverter on the desk.

## How go-sunspec is tested

The go-sunspec test suite needs no hardware. Since v0.5.0 the library can serve SunSpec devices, and its tests use that `Server` as the device: every read path is exercised over real Modbus TCP against a served chain whose values the test knows.

| Layer | What it covers |
|---|---|
| Unit | One function or type at a time: decoders and encoders per point type, scale factors, groups, the `Server`, tables of inputs and expected registers, values and errors. |
| Round trip | `EncodeModel` then `DecodeModel` for every model of the registry, with generated values for every point type, repeating groups included. |
| End to end | The library's `Server` behind a real go-modbus TCP server, read through `Detect`, `Discover`, `ReadAll`, `ReadModel`, `ReadModelByID` and `ReadPoint`: every registry model, every `DiscoverOptions` field, vendor models, request splitting, live updates, client writes and every documented error. The test file starts with a feature-to-test matrix. |
| Chaos | A fault-injecting TCP proxy between client and device (dropped, reset, truncated, stalled, split, duplicated, delayed and corrupted frames) and misbehaving devices (exceptions, a vanishing marker, a chain that changes or never ends, lying lengths, garbage registers). Asserted: no panic, no hang, no goroutine leak, and never a wrong value returned as valid. |
| Stress | Concurrent discovery and reads through one client, a pooled client and many clients while values are updated and clients write, across server stop and start; a read must never be torn or go back in time. |
| Generated registry check | A test fails if the committed `registry/models_gen.go` differs from what the generator produces from `models/`. |

The chaos tests found the two defects fixed in v0.5.0: reads through an existing `Device` decoded a changed device with its old layout, and an endless model chain looked complete. CI runs the tests with the race detector on Go 1.26 and 1.27, and `make check` enforces a coverage threshold that Codecov tracks.

```sh
make test       # tests with the race detector
make coverage   # coverage report for the library packages
make soak       # chaos and stress tests for SOAKTIME each (default 2m)
make check      # format, vet, lint, vulnerability scan, race tests, coverage gate
```

Randomized chaos runs log their seed; `SUNSPEC_CHAOS_SEED` replays one.

sunspecctl's own tests run against go-sunspec's `testutil` fixture server and against devices that `serve` runs in the same process, so every command, including `capture` and `serve`, is tested without hardware.

## sunspec-interop

sunspec-interop v0.3.0 (container contract 1.2) publishes two independent references, each in both roles:

| Image | Stack | Roles |
|---|---|---|
| `ghcr.io/otfabric/sunspec-interop-pysunspec2` | [pysunspec2](https://github.com/sunspec/pysunspec2) 1.3.7, the SunSpec Alliance's Python stack | device, client |
| `ghcr.io/otfabric/sunspec-interop-cbsigma` | [cB-Sigma sunspec](https://github.com/cB-Sigma/sunspec) v0.3.0 (client) and [sunspec-sim](https://github.com/cB-Sigma/sunspec-sim) v0.3.0 (device), Go, Apache-2.0 | device, client |

pysunspec2 has no Modbus server: in the device role it encodes the register map from a fixture, and a small Modbus TCP layer of the adapter serves those registers, so the SunSpec encoding is pysunspec2's and the transport is not. The cbsigma image is cB-Sigma's code on both sides, transport included.

The fixtures cover models 1, 101, 103, 111, 120, 123, 160 and, in the `der` fixture, the IEEE 1547-2018 models 701, 702, 704 and 705, at base addresses 0, 40000 and 50000: repeating and nested repeating groups (the volt-var curves of model 705), groups that occur once, not-implemented values, signed setpoints, 32-bit floats, 64-bit accumulators and scale factors from -3 to 3. The self-test of every release runs every client against every device, on amd64 and arm64, writes `results.json` in the organisation's interop-result-v1 format, and has no known differences. The two references differ without a case failing in two places: sunspec-sim encodes a `pad` point as 0x8000 and pysunspec2 as 0, and cB-Sigma's client refuses a write of a read-only point before sending it, where pysunspec2 sends it and the device refuses it.

```sh
git clone https://github.com/otfabric/sunspec-interop && cd sunspec-interop
make images smoke interop     # build, then self-test
make run-pysunspec2           # a device on 127.0.0.1:1502
```

### go-sunspec against the references

`make interop` in go-sunspec, and its Interop workflow, run against the sunspec-interop v0.3.0 images pinned by digest:

| Test | Direction | Shows |
|---|---|---|
| `TestGoReadsPeerDevice` | go-sunspec reads a device the peer encoded | The model chain and every raw and scaled point, nested repeating groups included, match what the peer's client reads from the same device |
| `TestPeerReadsGoServer` | The peer reads `Server` | The peer finds the device and reads the same points, and the registers equal those the peer encodes for the same values |
| `TestPeerWritesGoServer` | The peer writes `Server` | A write of a read-write point lands and one of a read-only point is refused, inside groups too (model 704's power factor, a point of a model 705 curve) |
| `TestGoWritesPeerDevice`, `TestGoWritesPeerDER` | go-sunspec writes the device | `WritePoint` of a scaled point, an enum, model 702 `WMax` and a curve adoption request lands and reads back; a read-only point is refused before anything is sent |

`WritePoint` writes top-level points only, so writes inside groups are shown only in the direction peer to `Server`.

### Test your stack against OT Fabric's

`ghcr.io/otfabric/sunspec-interop-otfabric` is go-sunspec behind the same container contract as the reference images (adapter name `otfabric`), so you can test your SunSpec client or device against it, the way OT Fabric tests its own stack against yours:

```sh
docker run -d --name go-sunspec -p 127.0.0.1:1502:1502 ghcr.io/otfabric/sunspec-interop-otfabric:<tag> server
until docker exec go-sunspec test -f /run/sunspec-interop/ready; do sleep 0.1; done
```

It is go-sunspec on go-modbus, serving the same fixtures as the references; its registers equal sunspec-sim's on every fixture. Its client does not declare `write-group`, since `WritePoint` writes top-level points only, so those cases are `unsupported` for it. `version` prints the versions inside the image.

Its tags are go-sunspec versions, such as `v0.10.0`, and `latest`; a rebuild of a version replaces its tag, so pin the digest when you need an exact build. It is not part of a sunspec-interop release or its `manifest.json`, and it reports `independentEngine: false`: a result against it tells you about your stack, not something independent about OT Fabric's. A result you publish, naming your implementation and version, is independent evidence. Like the references, it is for testing only and has no place on a network you do not control.

## Model definitions

The model definitions are the other half of correctness: if a definition is wrong, every decoded value from that model is wrong. go-sunspec takes them unchanged from the official [sunspec/models](https://github.com/sunspec/models) repository and generates the registry from them.

```sh
./check-models.sh         # report what is new, changed or removed upstream (read-only)
./check-models.sh --diff  # also show which points changed and the JSON diff
./sync-models.sh          # fetch the latest JSON from sunspec/models
make generate             # regenerate registry/models_gen.go
```

A scheduled workflow runs `check-models.sh` every week and opens an issue, with the changed points and the JSON diff, when upstream has new, changed or removed models. The issue closes itself once the local copy is back in sync. The model JSON files must not be edited by hand; a wrong definition is fixed upstream.

## Testing your own code

### Decode captured registers offline

If you have the raw registers of a model (from a capture, a log or a device manual example), decode them without any Modbus connection:

```go
meta := registry.ByID(103)
dm, err := sunspec.DecodeModel(regs, meta, instanceAddr)
```

`regs` has the same layout as `DecodedModel.RawRegisters`, which is indexed from the model's ID register, and `instanceAddr` is the model's address on the device. This is the quickest way to write table-driven tests for code that consumes `DecodedModel` values, including the "not implemented" and scale-factor cases.

### Serve a simulated device

`sunspecctl serve` runs a SunSpec device from a JSON file of point values by name. It is the quickest way to give an EMS, a data logger or your own go-sunspec code a device to read, and to see what it does with the writes it sends.

<Steps>

1. Start from the models you need, or copy a real device once:

   ```sh
   sunspecctl template --model 1,103,160 -o device.json
   # or
   sunspecctl capture --url tcp://192.168.1.10:502 -o device.json
   ```

2. Edit the values, then check the file without serving it:

   ```sh
   sunspecctl serve --file device.json --check
   ```

3. Serve it on loopback and point your code at it:

   ```sh
   sunspecctl serve --file device.json --url tcp://127.0.0.1:1502
   sunspecctl read --url tcp://127.0.0.1:1502
   ```

</Steps>

Serving a capture gives a device that reads the same as the original: the same points, values, scale factors and not-implemented points at the same addresses. With `capture --raw` the copy is identical register for register. A capture contains the device's serial number and network addresses, so look before you share it. See [Serving a simulated device](/docs/models/sunspec/cli/#serving-a-simulated-device) for the file format.

### Serve from your own tests

In Go, build the device in the test itself with `sunspec.NewServer` and serve it on a loopback port with go-modbus. Your test then controls every value, can change them with `SetPoint` or `Update` while your code polls, and can watch or refuse writes with `ServerOptions.OnWrite`:

```go
srv, _ := sunspec.NewServer(&sunspec.ServerOptions{BaseAddress: 40000, UnitID: 1,
	OnWrite: func(ctx context.Context, w *sunspec.ServerWrite) error {
		t.Logf("model %d: %v", w.ModelID, w.Points)
		return nil
	}},
	sunspec.ServerModel{ID: 1, Values: (&sunspec.Values{}).Set("Mn", "Test")},
	sunspec.ServerModel{ID: 103, Values: (&sunspec.Values{}).Set("W", 4200).Set("W_SF", 0)},
)
go srv.Serve(ctx, &modbus.ServerConfig{URL: "tcp://127.0.0.1:1502"})
```

### Other simulators

- [modbus-simulator](/projects/modbus-simulator/) serves a Modbus device from a JSON fixture of raw registers and codec fields and records a trace you can assert on in CI. It has no SunSpec support, so you lay out the marker, model headers and bodies yourself; use it when you need its fault injection or trace assertions.
- `modbusctl client scan --algo sunspec` records every model body to an [MBCAP capture](/docs/protocols/modbus/captures/), and `modbusctl server static` serves such a recording back at the Modbus level.

## What has been validated

<Aside type="note" title="Validation status">
- go-sunspec v0.10.0 is tested against two independent SunSpec implementations, pysunspec2 1.3.7 and cB-Sigma sunspec and sunspec-sim v0.3.0, in both directions, on the models of the sunspec-interop fixtures (see above). Other models, vendor models, Modbus RTU and real devices are not in that suite.
- Its own tests run against its `Server`, its `testutil` fixture server and offline decoding. The client and the server share the model definitions and the codecs, so those tests prove that both sides agree with each other and with the definitions; the interop suite is what shows agreement with others. Nothing is certified by the SunSpec Alliance.
- The underlying Modbus TCP transport (go-modbus) is tested against five independent Modbus TCP stacks. That covers the wire protocol, not SunSpec decoding or encoding.
- Contributors are asked to verify changes that affect what is read from a device against real hardware when possible, and to name the device in the pull request. The repository does not publish a list of devices it has been verified against.
</Aside>

If go-sunspec decodes a value wrongly on your device, the repository asks for the manufacturer and model, the transport, and the output of `sunspecctl detect`, `sunspecctl models` and `sunspecctl read --raw` in the issue.
