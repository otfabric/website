Nobody connects a plant, a substation or a building with one library. Every integration leans on stacks written by other people: a C library in a gateway, a Python tool on a laptop, a Java server in a SCADA system, a vendor SDK inside a controller. OT Fabric only makes sense as part of that ecosystem, which is why each of our protocols ships with an interop suite that tests against the established implementations.

So we mapped the ecosystem. This post is the research: fifteen protocol families, one application profile on top of MQTT, 268 implementations, and what we learned checking every one of them against its own release channel. The interactive version lets you pick a protocol or a profile, filter by language, licence and activity, and jump straight to the source.

## How we counted

We sort every implementation into one of four groups, because a flat list of repositories hides how the ecosystem actually fits together:

- **Independent stacks** handle the protocol themselves.
- **Derived libraries and bindings** wrap, port or extend another stack. They link to their upstream instead of counting as a new engine.
- **Commercial SDKs** are proprietary or dual-licensed developer libraries, including those without public source.
- **Legacy and reference** code is historically important but superseded or no longer maintained.

Each entry records its language, licence (as an SPDX expression, read from the licence file, or the licence's own name where it has no SPDX identifier), protocol roles, documented capabilities, latest release, last commit, stars and forks, and the OT Fabric interop suite that exercises it, if any. Every entry also lists its sources and the date we last verified it.

<Callout title="Popularity is a property, not a ranking">
  Stars measure attention from software developers, not field deployments. A mature C stack with 200 stars may run in more devices than a library with several thousand. The map draws every implementation at the same size on purpose.
</Callout>

## GitHub Releases are the wrong place to look

The first draft of this inventory took versions from GitHub Releases. Checking each project against the channel it actually publishes to changed a third of the version column:

- **NModbus** has no GitHub Release objects, but publishes 3.0.83 on NuGet (April 2026).
- **jsmodbus** shows v2.0.1 as its GitHub Release; npm has 5.0.0, published in September 2026.
- **Modbus4J** is at tag v3.1.0, ahead of its old 2.x GitHub Release.
- **BACnet Stack** releases on SourceForge (1.6.1, August 2026), not as GitHub Releases. The project dates back to 2004; the GitHub repository only to 2019.
- **BACpypes3** is at 0.0.110 on PyPI and **System.IO.BACnet** at 4.0.0 on NuGet. Its MIT licence, unclear in the first pass, is confirmed.
- **tokio-modbus** (0.17.0), **simonvetter/modbus** (v1.6.4) and **NModbus** tag and publish without creating GitHub Releases.
- The **EPRI OpenADR** reference code is BSD-3-Clause throughout; two licences had been left open.

The registry now names the source of every version: GitHub, PyPI, npm, crates.io, NuGet, Maven Central, pub.dev, SourceForge, the Go module proxy or a vendor's release notes.

## Modbus

**Very mature.** The broadest open-source ecosystem in OT, from microcontrollers to cloud services. Modbus TCP versus serial is a capability, not a separate implementation, and so is client-only versus client and server.

<LandscapeTable protocol="modbus" />

libmodbus, PyModbus, NModbus, digitalpetri/modbus and tokio-modbus are the reference implementations in our [modbus-interop](https://github.com/otfabric/modbus-interop) suite. goburrow/modbus and ModbusMaster are still widely used but have not changed since 2016 to 2018. On the commercial side, Triangle MicroWorks sells Modbus source libraries, and Modbus4J is dual-licensed by Radix IoT.

## OPC UA

**Very mature, with a strong commercial market.** OPC UA lets you compare independent open source, foundation-backed code and proprietary SDKs side by side. Client/server and PubSub are separate capabilities, and no stack covers every security profile, transport and information model.

<LandscapeTable protocol="opc-ua" />

open62541, Eclipse Milo, the OPC Foundation .NET stack, node-opcua and the FreeOpcUa family are the essential open-source references, and six of them run in our [opcua-interop](https://github.com/otfabric/opcua-interop) suite: open62541, Eclipse Milo, UA-.NETStandard, node-opcua, opcua-asyncio and async-opcua. Their PubSub support differs sharply: open62541 and the .NET stack implement it, Milo, async-opcua and opcua-asyncio do not, and for node-opcua it is a commercial add-on. The UA JSON mappings of HTTPS and WebSockets are rarer still: of the six, only the .NET stack serves them. Two lineages are worth knowing: python-opcua is deprecated in favour of opcua-asyncio, and the Rust code base started by locka99/opcua continues as async-opcua. Unified Automation, Prosys and Softing are the established commercial SDK vendors. OpenOpcUa CoreServer, the native C/C++ runtime behind 4CE Industry's OOUAMiddleware, takes another route: closed source, but free to deploy without licensing fees.

## BACnet

**Mature, but fragmented.** BACnet/IP, MS/TP, BACnet/SC and the device profiles make very different demands, so "BACnet supported" on its own says very little. The map records which data links each stack documents.

<LandscapeTable protocol="bacnet" />

BACnet Stack stands out: extensive service coverage, embedded targets, and a GPL linking exception that lets proprietary products link it. BACpypes3, BACnet4J and System.IO.BACnet (the stack behind YABE) complete the reference set, and all four run in [bacnet-interop](https://github.com/otfabric/bacnet-interop). BACpypes3 now also ships an MCP server, so AI agents can talk BACnet. Cimetrics, PolarSoft and SoftDEL lead the commercial SDK market.

## IEC 60870-5-104

**Specialized.** A handful of credible engines, with bindings and forks built on top of them, which is exactly where the relationships matter.

<LandscapeTable protocol="iec-104" />

The independent engines are lib60870, OpenMUC j60870 and go-iecp5. The Python package c104 binds lib60870; wendy512/iec104 builds on a go-iecp5 fork. The original go-iecp5 was archived in March 2023 and lives on in two maintained forks. cB-Sigma's iec60870 is a young pure Go stack (Apache-2.0) with IEC 101, a 101-to-104 gateway and the only open-source implementation of the 2023 edition of IEC 62351-5 application-layer security. Four of them run in [iec104-interop](https://github.com/otfabric/iec104-interop): lib60870, j60870, wendy512/iec104 and cB-Sigma iec60870. j60870 is distributed through OpenMUC and Maven Central (1.8.0) rather than a GitHub repository. MZ Automation, OpenMUC and Triangle MicroWorks offer commercial licences.

## IEC 61850

**Specialized, with few comprehensive implementations.** IEC 61850 is not just MMS: it adds information models, GOOSE, Sampled Values and SCL. A stack that only speaks MMS is not an IEC 61850 stack.

<LandscapeTable protocol="iec-61850" />

libiec61850 is the dominant open-source reference: MMS client and server, GOOSE, Sampled Values, reports, datasets, logging, file services and TLS, with commercial licences from MZ Automation. IEC61850bean (formerly OpenIEC61850) is an established Java MMS implementation, quiet since 2023. Two young stacks cover the whole family. dscsystems/go-iec61850 (Go, GPL-3.0, started in July 2026) adds R-GOOSE, R-SV and IEC 62351 security to MMS, GOOSE and Sampled Values. iec61850-rust (Rust, MIT OR Apache-2.0, September 2026) was written from the published standards as a set of crates, with MMS, GOOSE, 9-2LE Sampled Values and IEC 62351-3 TLS, and lists its gaps openly. All four run in [iec61850-interop](https://github.com/otfabric/iec61850-interop), formerly mms-interop.

## Siemens S7

**Mature for classic S7comm, constrained beyond it.** Talking to an S7-300 over ISO-on-TCP is not the same as talking to an S7-1500 with optimized data blocks and access protection. S7comm and S7commPlus are separate branches on the map.

<LandscapeTable protocol="s7" />

Snap7 is distributed on SourceForge; the popular GitHub repository under SCADACS is a fork with server extensions, not the canonical source. python-snap7 is no longer a wrapper: since 3.0 (March 2026) it implements TPKT, COTP and S7 natively in Python. Apache PLC4X counts stars for its whole multi-protocol framework. The new s7commplus project opens the S7-1200/1500 branch. Softing siAccess, successor to ACCON-AGLink, and PLCcom for S7 are the commercial options.

## OpenADR

**Smaller and still evolving.** OpenADR 2.0b and 3.x are different technologies, and 3.1 is not backward-compatible with 3.0, so the map separates versions and roles: VEN, VTN and business logic.

<LandscapeTable protocol="openadr" />

OpenLEADR covers both generations: Python for 2.0b, Rust for 3.1, where its README is upfront that subscriptions (webhooks) are not supported yet. ElaadNL's openadr3-client comes from an organization that builds EV charging infrastructure. The EPRI projects are legacy references; EPRI has discontinued support. The OpenADR Alliance's reference implementation is not publicly available, so it is not on the map, and we found no standalone commercial OpenADR SDKs comparable to other protocols. That branch stays open for verified submissions.

## OCPP

**Mature for 1.6J, maturing for 2.x.** OCPP 2.0.1 is not backward-compatible with 1.6, while 2.1 extends 2.0.1, so a claim of "OCPP support" says little without the version. The map lists versions and roles: the charging station and the CSMS.

<LandscapeTable protocol="ocpp" />

The open-source side is broad, with libraries in Python, Java, Go, C++, Rust, JavaScript, C# and Kotlin. Five of them run in [ocpp-interop](https://github.com/otfabric/ocpp-interop): The Mobility House ocpp, ChargeTimeEU Java-OCA-OCPP, ocpp-go, EVerest libocpp and CitrineOS. libocpp's own repository is archived; it now lives inside EVerest, the LF Energy charging station stack. SteVe and OCPP.Core are complete CSMS products rather than libraries, and MicroOcpp brings the station side to microcontrollers. Commercial stacks are sold for both sides, though versions and platforms are rarely published.

## DNP3

**Mature, with few active open stacks.** DNP3 (IEEE 1815) has been the SCADA protocol of North American utilities for three decades, and the commercial side is well established: source code libraries from Triangle MicroWorks, FreyrSCADA and others run inside many RTUs and IEDs. The open-source side has thinned out.

<LandscapeTable protocol="dnp3" />

opendnp3, for a decade the default open-source stack, was archived in September 2022 at 3.1.2, and still sits under the Python bindings pydnp3, VOLTTRON's dnp3-python and the new yadnp3 fork. Step Function I/O's Rust library, with C, C++, .NET and Java bindings, is actively maintained, but its licence allows non-commercial, non-production use only, with a commercial licence for production: the map files it under its own licence family, source-available. The rest is young: DSC Systems' go-dnp3 (GPL-3.0) and cB-Sigma's dnp3 (Apache-2.0) are pure Go stacks from 2026, both with Secure Authentication, and dnp3py brings a pure Python master and outstation with a MESA DER profile. Four of them run in [dnp3-interop](https://github.com/otfabric/dnp3-interop): Step Function I/O, opendnp3, DSC go-dnp3 and dnp3py. The Triangle MicroWorks adapter is on hold until its licensed source has an agreed way into the builds.

## IEEE 2030.5

**Young, and shaped by two mandates.** IEEE 2030.5 (Smart Energy Profile 2.0) carries export limits, schedules and prices from utilities and aggregators to inverters, batteries and chargers. California's Rule 21 made it the default for smart inverters through CSIP, and Australian distributors use CSIP-AUS for dynamic operating envelopes, so most of the open field is a research lab's, a utility programme's or one developer's answer to one of those two profiles.

<LandscapeTable protocol="ieee-2030-5" />

The Australian side is the most active: ANU's Envoy is a complete CSIP-AUS utility server, with its document models and the CACTUS test harnesses built around it, and open-dynamic-export is a CSIP-AUS client that drives home solar and batteries. In the US, PNNL's GridAPPS-D, whose Python server never got past alpha releases, published a Go server and client in 2026, DER Security's py20305 is a new client for CSIP and CSIP-AUS, and VOLTTRON has an agent that connects its devices to a server. The EPRI client, written for California's certified open-source programme, is the oldest open stack and has not changed since 2018. Four of them run in [ieee20305-interop](https://github.com/otfabric/ieee20305-interop): Envoy, GridAPPS-D (server and client), py20305 and the EPRI client. Commercially, embedded clients such as Kitu's sit next to the test systems that certification runs on, and few vendors publish versions.

## EtherNet/IP

**Mature for tag access, thin for I/O.** EtherNet/IP carries CIP, the Common Industrial Protocol that ODVA maintains, between PLCs and the I/O adapters, drives and devices they scan, and it is the native network of Rockwell Automation's ControlLogix and CompactLogix controllers. The commercial side is very established: source code stacks, chip firmware and controller runtimes from RTA, Hilscher, Pyramid Solutions, CODESYS and Beckhoff sit behind thousands of certified products.

<LandscapeTable protocol="ethernet-ip" />

Most of the open field reads and writes Logix tags: libplctag (C, with a .NET wrapper and many others), pylogix, pycomm3, node-ethernet-ip, rseip, gologix and loki-os's go-ethernet-ip, and ORNL's EPICS driver and its Java counterpart, which have connected accelerator control systems to Logix controllers for two decades. Open stacks with cyclic I/O are fewer: OpENer, first released by Rockwell Automation and still the only widely used open adapter, EIPScanner and EEIP.NET as scanners, gologix's adapter and the alpha I/O scanner of st-ethernet-ip. Twelve of them run in [ethernetip-interop](https://github.com/otfabric/ethernetip-interop): OpENer, EIPScanner, pycomm3, cpppo, libplctag, gologix, pylogix, etherip, eip-rs, node-ethernet-ip, EEIP.NET and loki-os go-ethernet-ip. None of the open stacks documents an ODVA conformance test; the specifications are sold by subscription, so open implementers work from public documents and from each other's behaviour.

## PROFINET

**A mature market, a thin open field.** PROFINET IO, maintained by PROFIBUS & PROFINET International (PI), is the industrial Ethernet of Siemens SIMATIC controllers and of the many drives, I/O systems and field devices built to work with them. Certification is mandatory for every device, and the stacks behind certified products are almost all licensed: Siemens' development kits, Hilscher's netX firmware, Softing and Phoenix Contact protocol software, and the controller runtimes of CODESYS and Beckhoff. PI's own Community Stack is free, but only for members, and its licence forbids combining it with copyleft code.

<LandscapeTable protocol="profinet" />

In the open field, rt-labs p-net is the one widely used IO-Device stack, dual-licensed GPL-3.0 and commercial; since 2024 its public repository is an evaluation snapshot without build files or ports, so open projects build its last complete tree from 2023. Everything else is young or small. pnio-rs is a 2026 Rust IO-Device for Linux, OpenPNIO an IO-Device core that says itself it is not functional yet, and profinet-py, with its Rust port profinet-rs, is the only open IO-Controller next to go-profinet. Most other projects are DCP tools that find devices and set their names and addresses: pnio-dcp, ProfinetTools, OpenProfinet and a Node.js addon. Four of them run in [profinet-interop](https://github.com/otfabric/profinet-interop): p-net, pnio-rs, profinet-py and pnio-dcp, next to two MRP ring implementations. None of the open stacks implements IRT, which needs switch hardware, and only p-net reports a pass of PI's test bundle.

## CAN bus

**Very mature, centred on one kernel.** CAN is older and more widespread than any other protocol on the map: every car, truck and tractor, most battery packs and chargers, and many machines run it. The open field looks different from the rest because it has a centre. Since 2008 the Linux kernel treats CAN controllers as network interfaces, SocketCAN, and almost every open tool is a client of it: can-utils, whose candump log is the common trace format, python-can, which also drives the PEAK, Kvaser and Vector adapters, and bindings for Rust, Go, Java, .NET and Node.js. The kernel has carried ISO-TP since 5.10 and CAN XL since 6.2.

<LandscapeTable protocol="can-bus" />

Above the frames, the databases that give them meaning have their own ecosystem. DBC has no public specification, so cantools and canmatrix, which read DBC, KCD, ARXML and more, act as references, and comma.ai's opendbc collects reverse-engineered DBC files for hundreds of car models. The commercial side is mostly the adapter vendors: Vector, PEAK and Kvaser give their APIs away with their hardware and sell analysis tools such as CANoe. CAN XL is the young part: of the open stacks, only the kernel, can-utils, SocketCANSharp and go-canbus handle CAN XL frames so far. Eight of them run in [canbus-interop](https://github.com/otfabric/canbus-interop) or through it: can-utils with the kernel's CAN_RAW and ISO-TP, python-can, socketcan-rs, Scapy, python-can-isotp, cantools and canmatrix. CAN is the transport here, and the protocols on top of it are mapped apart: CANopen has its own entry below, and J1939 and UDS stacks are not on the map yet.

## CANopen

**Mature, with three open stacks carrying the field.** CANopen is the protocol on top of CAN in industrial machines, drives, lifts, medical and mobile equipment, so it gets its own entry next to the transport. The open field is older than most on this map and smaller than CAN's. CANopenNode (C, Apache-2.0) is the most used device stack, on microcontrollers and on Linux as CANopenLinux, with CANopenEditor to generate its object dictionaries from EDS files. Lely CANopen (C and C++, Apache-2.0) has the most complete master, with the CiA 302 boot-up, and ROS 2's ros2_canopen builds on it. python canopen (MIT) is what test benches and commissioning scripts use. Around them: CanFestival, one of the oldest stacks, kept alive by the Beremiz project without releases; Embedded Office's device stack, open-sourced under Apache-2.0 and quiet since 2022; node-canopen for Node.js; gocanopen and now go-canopen in Go; and three young Rust stacks, zencan, canopen-rs and oze-canopen, the first two aimed at no_std microcontrollers.

<LandscapeTable protocol="canopen" />

The commercial side is where most CANopen devices come from: emotas, port and Embedded Systems Academy's MicroCANopen sell C source stacks, HMS sells a CANopen master for its Ixxat interfaces, and CODESYS controllers run CANopen managers and devices. CANopen FD is the young part: none of the three open references implements CiA 1301 yet. The three run in [canopen-interop](https://github.com/otfabric/canopen-interop), as devices and as masters, with LSS, MPDOs and the CiA 302 boot-up where each stack has them.

## KNX

**Mature, with a strong open field on the IP side.** KNX is the building control standard of switches, dimmers, blinds, heating valves and presence detectors, from homes to offices and hotels. Devices sit mostly on twisted pair; servers, visualizations and gateways reach them through KNXnet/IP interfaces and routers, and that IP side has four mature, independent open stacks. Calimero (Java, GPL-2.0 with the Classpath exception) has the library, a KNXnet/IP server and command-line tools, with KNX IP Secure and Data Secure; its stable release is 2.6, and version 3 has been published as milestones since 2025, with 3.0-M2 in April 2026. knxd (C++, GPL-2.0), the fork of eibd, runs inside many Linux gateways, routes between interfaces and serves tunnelling. xknx (Python, MIT) is the engine of Home Assistant's KNX integration, and KNXUltimate (TypeScript, MIT) of node-red-contrib-knx-ultimate, both with KNX Secure. openHAB's binding embeds Calimero, so it does not count as an engine of its own.

<LandscapeTable protocol="knx" />

Around them, the older libraries have gone quiet: knx-go for Go says it is no longer maintained, KNX.net for .NET and esp-knx-ip for the ESP8266 have not changed in years, and knx.js on npm last released in 2024. The newcomers are in Rust, knx-rs, knust and KNXyz, all from 2026. On the device side, thelsing's knx stack and its OpenKNX fork run on ESP32, RP2040 and other microcontrollers and are programmed with ETS, while certified commercial stacks such as TAPKO's KAIstack sit in most products. KNX Association publishes its own .NET Falcon SDK on NuGet, and had Cascoda build an open-source stack for KNX IoT, which is not KNXnet/IP and is not on the map. Calimero, knxd, xknx and KNXUltimate run in [knx-interop](https://github.com/otfabric/knx-interop), with a raw probe for malformed input.

## Sparkplug B, an application profile

**A mature reference, a young independent field.** Sparkplug B is not a protocol of its own: it is a profile of MQTT that fixes a topic namespace, a Protobuf payload and session state, so that edge nodes and SCADA hosts from different vendors share one broker. The map keeps it apart from the fifteen protocols for that reason, as the first [application profile](/profiles/sparkplugb/). The specification, Eclipse Sparkplug 3.0.0, is free to implement and was adopted as ISO/IEC 20237:2023.

<LandscapeTable protocol="sparkplug-b" />

Eclipse Tahu is the Working Group's own code: a Java edge node and host, a JavaScript edge client, and payload libraries for C and Python, all under EPL-2.0, which several other stacks reuse through the shared `sparkplug_b.proto`. Most of the independent field is recent. SparkplugNet (C#) and srad (Rust) implement both roles, pysparkplug (Python) the edge node, and sparkplughost (Go) only the host; since 2025 HiveMQ's .NET client, SparklerNet, PlugB and Joy Automation's nautilus and Synapse have joined. Few combine both roles with primary host awareness, server walking and resequencing of out-of-order messages. Six of them run in [sparkplugb-interop](https://github.com/otfabric/sparkplugb-interop): Tahu in Java and JavaScript, pysparkplug, SparkplugNet, srad and sparkplughost.

The commercial side looks different from the other protocols: few SDKs, and most Sparkplug lives inside products. Cirrus Link, which contributed Sparkplug to the Eclipse Foundation, sells the MQTT modules for Ignition; HiveMQ's broker is Sparkplug aware; historians from Canary and GE Vernova collect as host applications; EMQ's NeuronEX and Opto 22's groov controllers publish as edge nodes. The Eclipse Foundation runs a self-certifying Sparkplug Compatible program around its TCK. The map records what each project documents, not whether it is listed there.

These are judgements about maturity and visibility, not measured conformance, security or quality. Our interop suites are where we test behaviour; this map is where we record who is out there.

## Help us complete it

This is a strong baseline, not an audited directory. We know it misses implementations outside GitHub, commercial SDK details (versions, platforms, evaluation editions) and capability evidence beyond what each README claims.

The whole map is one JSON file, [`src/data/ecosystem.json`](https://github.com/otfabric/website/blob/main/src/data/ecosystem.json), with sources and a verification date on every entry. Open a pull request to add a stack, a commercial SDK, a correction or interop results, and the map updates when it merges. Maintainers are especially welcome to check their own entries.
